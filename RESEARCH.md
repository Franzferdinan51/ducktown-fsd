# FiveM TaskVehicleDriveToCoordLongrange crawling at ~1 m/s — Research Report

Read 2026-11-27. Flags: **[verified live]** = page opened and read in research browser; **[index]** = search-index text only (still the source's own text, not opened live).

## Summary — the short answer

The task call itself, the speed units, and the style values in the setup are **not** the bug — they are byte-for-byte what a known-working player autopilot uses. Bucko_autopilot is a single call `TaskVehicleDriveToCoordLongrange(playerPed, vehicle, dest.x, dest.y, dest.z, 30.0, 786603, 10.0)` with **no** `SetDriveTaskCruiseSpeed` / max-speed call on start **[verified live]**. So the crawl is almost certainly something *added on top of, or already present on, this server* that caps the drive task or fights it, and the three symptom clues point that way:

1. **Fast start → crawl to ~1 m/s → stop** = the task's own speed takes effect first, then a cap takes over — either a per-frame/periodic setter (`SetDriveTaskCruiseSpeed`, `SetDriveTaskMaxCruiseSpeed`, a road-node speed zone) or the road-node speed the task obeys once it joins the network.
2. **Fast OFF-road, slow ON-road** = the cap lives in the **road-node layer** (node speed attribute / `AddRoadNodeSpeedZone`), not in the vehicle. Off-road there are no nodes to obey; manual driving ignores node speeds entirely, which also explains "manual is fine."
3. **REVERSE reaches full speed** = rules out vehicle-global caps (power/torque multiplier, `SetEntityMaxSpeed`, fuel, handling) as the primary cause — those cap reverse and manual too. It fits (a) a forward drive-task cap, and (b) an injected **brake** control (`SetControlNormal(0, 72, …)`), because in GTA control 72 is brake in forward gear and *accelerator* in reverse gear.

**First three tests (minutes, in order):** (1) delete both post-task cruise/max calls and re-test — Bucko proves they are unnecessary; (2) `grep -r` every resource on the server for `SetDriveTaskCruiseSpeed`, `SetDriveTaskMaxCruiseSpeed`, `AddRoadNodeSpeedZone`, `SetControlNormal`, `SetDriveTaskDrivingStyle`, `ClearPedTasks` and stop the hits / bisect resources; (3) run the identical task on a freshly spawned **NPC** ped and on a clean test server — NPC-fast/player-slow = player-control or player-task interference; both-slow-on-road = node/speed-zone layer.

## Findings

### 1. Known causes for a PLAYER ped crawling — style flags, road-node speed, cruise/max natives

**Decoding the styles actually tried (important correction to a hypothesis in the mission):**

From the official `citizenfx/natives` enum **[verified live]** — https://github.com/citizenfx/natives/blob/HEAD/TASK/SetDriveTaskDrivingStyle.md

| Flag | Value | In 786603? | In 447? |
|---|---|---|---|
| StopForVehicles | 1 | ✅ | ✅ |
| StopForPeds | 2 | ✅ | ✅ |
| SwerveAroundAllVehicles | 4 | ❌ | ✅ |
| SteerAroundStationaryVehicles | 8 | ✅ | ✅ |
| SteerAroundPeds | 16 | ❌ | ✅ |
| SteerAroundObjects | 32 | ✅ | ✅ |
| StopAtTrafficLights | 128 | ✅ | ✅ |
| GoOffRoadWhenAvoiding | 256 | ❌ | ✅ |
| AllowGoingWrongWay | 512 | ❌ | ❌ |
| **AdjustCruiseSpeedBasedOnRoadSpeed ("match road speed")** | **16384** | **❌** | **❌** |
| UseShortCutLinks | 262144 | ✅ | ❌ |
| ChangeLanesAroundObstructions | 524288 | ✅ | ❌ |
| UseSwitchedOffNodes | 2097152 | only in variant 3 | ❌ |

`786603` is literally the named preset `DrivingModeStopForVehicles = StopForVehicles|StopForPeds|SteerAroundStationaryVehicles|SteerAroundObjects|StopAtTrafficLights|UseShortCutLinks|ChangeLanesAroundObstructions` in that same official file **[verified live]**, and the preset "Normal, 786603" on the calculators **[index]** — https://fivemad.com/tools/driving-style-calculator

Consequences:

- **Bit 16384 is NOT in any style tried**, so "the style is matching road speed" cannot be the explanation *unless another resource re-sets the style after the task starts* via `SetDriveTaskDrivingStyle`. Note also the flag's documented scope: "Cruise tasks only: adjusts the cruise speed to each road's speed" **[index]** — https://fivemad.com/docs/tools/driving-style-calculator — i.e. it is described for wander/cruise tasks, not as the mechanism that caps a goto/longrange task.
- What 786603 *does* contain that can produce a full stop on an empty-looking road: **StopForVehicles (1) + StopForPeds (2) + StopAtTrafficLights (128)**. Any vehicle/ped the task perceives ahead — including a parked vehicle it fails to steer around, a ped, or a red light / stop line — is a legitimate brake-to-stop. Diagnostic style to strip all of these is `786468` (`DrivingModeAvoidVehiclesReckless`: Swerve|SteerAroundObjects|UseShortCutLinks|ChangeLanes, no stop-for-peds, no lights) or simply `0`, from the same official enum **[verified live]**.
- **Neither tried style contains AllowGoingWrongWay (512).** Vespura's description: wrong-way driving "only does it if the correct lane is full, will try to reach the correct lane again a.s.a.p." **[verified live]** — https://www.vespura.com/fivem/drivingstyle/ . A car that starts facing *against* its route's node direction, or whose route joins a one-way/divided road against traffic, will creep, hesitate and try to regain the correct lane instead of just driving — a classic "starts, crawls, stops" on-road-only pattern (off-road there is no lane direction to regain).
- **UseSwitchedOffNodes (2097152)**: "Routes over nodes switched off for traffic (goto tasks only)" **[index]** — https://fivemad.com/docs/tools/driving-style-calculator . If any resource/MLO has switched nodes off (`SetRoadsInArea`), adding this bit can route the task *onto* dead nodes where it stalls; removing it can equally strand a route that needs them. It is a route-availability bit, not a speed bit.
- **ForceJoinInRoadDirection (1073741824)**: "When joining a road, always joins in the direction of traffic" **[index, same source]**. Forced joining can make the car crawl to a legal join point / loop around rather than crossing to the far lane — it makes wrong-direction starts *slower*, not faster.

**Road-node speed is real, per-node, and the longrange task obeys the road layer regardless of the 16384 bit:**

- Vehicle nodes carry their own speed: the `.ynd` node record holds "the speed, the density, off road, highway, tunnel…" and the editor exposes node **Speed = Slow / Normal / Fast / Faster**, with lane counts (0–7 each way) per link **[index]** — https://fivemad.com/tools/ynd-editor
- Per-node speed limits in the path data: "Speed limit can only be set for each 'vnode'. Usually, the nodes of the same street have the same speed limit" **[index]** — https://gtaforums.com/topic/880868-how-to-get-the-speed-limit-of-the-streetroadfreeway/
- Empirical Cfx research on `GetVehicleNodeProperties`: flag **2 = mainly ~50 km/h city roads; flag 10 locations (parking lots, driveways, gas stations, LS Airport) — "nearly all vehicles I've seen at flag 10 locations were driving EXTREMELY slow"; 66 = freeway** **[index]** — https://forum.cfx.re/t/getvehiclenodeproperties-get-current-zone-or-road-speed-info-research/4333996
- Bucko user report, with plain 786603: the car "will follow the road and **adjust for traffic speed, traffic and even stop at lights**" **[verified live]** — https://forum.cfx.re/t/autopilot-standalone-free-release/5330653 . So a longrange task's *effective* speed on-road is `min(task speed, node/traffic/light constraints)` even without bit 16384; off-road (navmesh/direct) that constraint disappears — matching the reported off-road-fast/on-road-slow split.
- **`AddRoadNodeSpeedZone` is a server-content suspect, not just theory:** a traffic-light sync resource uses "a 'Speed Zone' `AddRoadNodeSpeedZone` with a speed of 0. Then later remove it… These speed zones cause NPCs to stop right at them, they don't even complain about being stopped, you can leave them stopped as long as you want" **[index]** — https://forum.cfx.re/t/sync-traffic-lights/4871954 . Prop/traffic-management resources place such zones routinely. A leftover or oversized zone with speed ≈0–5 near the start of the route produces exactly *fast approach → crawl → stop, on-road only, manual unaffected* (speed zones only govern AI driving). This is checkable only by grepping/stopping resources — zones are not readable back from a native.

**Units/semantics of the speed natives — all m/s, and cruise speed *is* the task's target speed:**

- Task speed is m/s: Vespura's example, "speed = 20.0 — averages around 45 mph top speed" for a **player** ped, used identically for `TaskVehicleDriveWander` and `TaskVehicleDriveToCoordLongrange` **[verified live]** — https://www.vespura.com/fivem/drivingstyle/
- Forum confirmation in the other direction: to slow a bus to 50 km/h, "Change the 70.0 of TaskVehicleDriveToCoordLongrange to 13.8" **[index]** — https://forum.cfx.re/t/advanced-public-transport-ai/4914540
- `SET_DRIVE_TASK_CRUISE_SPEED(Ped driver, float cruiseSpeed)` (0x5C9B84BD7D31D908) — "Sets the cruise speed of the drive task of driver" **[index]** — https://the-lab.oxdev.fr/redm/natives/task/set_drive_task_cruise_speed
- The max native's real name is **`SET_DRIVE_TASK_MAX_CRUISE_SPEED`** (0x404A5AA9B9F0B746) — "Sets the **maximum cruise speed** of the drive task of ped to maxCruiseSpeed" **[index]** — https://the-lab.oxdev.fr/redm/natives/task/set_drive_task_max_cruise_speed . The cfx-client task module lists `set_drive_task_cruise_speed` and `set_drive_task_max_cruise_speed` and **no `set_drive_task_max_speed`** **[index]** — https://docs.rs/cfx-client/latest/i686-pc-windows-msvc/cfx_client/natives/task/index.html
  - ⚠️ **Naming trap for Q1/Q2:** if the resource literally calls `SetDriveTaskMaxSpeed(...)` (the name in the mission statement), that is not the documented native name. Depending on runtime/language that call is a nil-function error (killing the thread that issued the task — check F8) or a no-op. The documented call is `SetDriveTaskMaxCruiseSpeed`.
  - Semantics if called correctly: cruise speed **replaces** the task's current target speed (it is not a multiplier and not "in addition to" the task argument), and max-cruise is a **ceiling on cruise**. Either one set to a small value caps the task far below its own speed argument — e.g. cruise = 1.0 gives exactly the reported ~1 m/s crawl. Both take the same m/s scale as the task (all worked examples pass 8.0–50.0 / 300.0 in the same units as task speeds, see §2).

### 2. Does calling SetDriveTaskCruiseSpeed / MaxCruiseSpeed AFTER the task interfere?

**Ordering alone: no — after-the-task is the documented, intended way to change a running drive task's speed.** A Cfx thread does exactly this in a 100 ms loop after the task: highway `SetDriveTaskCruiseSpeed(copPed, 50.0)`, ramp `12.0`, entry `8.0` **[index]** — https://forum.cfx.re/t/help-taskvehicledrivetocoords/385994 . Others set cruise right after `TaskVehicleChase` (`35.0`, even `300.0`) **[index]** — https://forum.cfx.re/t/issue-with-my-fivem-server-pull-me-over-script/5301994 , https://github.com/citizenfx/fivem/issues/1828

**But three real interference modes exist:**

1. **It overrides, so any wrong/small value wins.** Because cruise replaces the target, the pair in the setup is redundant at best: `CruiseSpeed(speed)` already sets the target; `MaxCruiseSpeed(speed+5)` only matters if something later raises cruise. If *any* code path passes a converted/shadowed value (e.g. a km/h→m/s division applied twice, a statebag/limiter value, or `1` as an integer in a JS resource where the native expects a float), the task will faithfully crawl at that value. No source was found documenting these natives "resetting" or corrupting a task when passed correct m/s values — the risk is value, not ordering.
2. **The stop-path leak:** in Bucko, `SetDriveTaskCruiseSpeed(playerPed, 0.0)` appears **only in the stop handler**, together with `ClearPedTasks` **[verified live]** — https://forum.cfx.re/t/autopilot-standalone-free-release/5330653 . Any resource (including a previous/stale instance of an autopilot or a cruise-control resource) that runs its stop/cancel path, or that periodically re-asserts a stored cruise value of 0/1, will cap a *new* task on the same ped. Drive-task cruise is per-ped state, not per-resource.
3. **They are unnecessary for this use case:** both working player autopilots found (§4) use neither call on start. **Fix/test: delete both calls; if speed then works, re-add only `SetDriveTaskCruiseSpeed` with a printed/logged value and verify the logged value is the intended m/s float.**

### 4. Longrange vs TaskVehicleDriveToCoord for player peds; what working autopilots actually use

- **Longrange is the correct choice for cross-map player autopilot, and is what working resources use.** Rationale given on Cfx for preferring it: "Many AI tasks will stop running for the ped once a player is > 300 m or so away" with the short task **[index]** — https://forum.cfx.re/t/help-taskvehicledrivetocoords/385994 . That 300 m failure mode is about an *NPC* driver relative to a player; for the player's own ped the distance is zero, so it is **not** a plausible cause here.
- Longrange's own weakness is its route layer: "`TaskVehicleDriveToCoordLongrange` uses the long range map mesh to navigate… if you are having problem with the navigation use the simpler one, `TaskVehicleDriveToCoord`" **[index]** — https://forum.cfx.re/t/having-trouble-getting-a-npc-to-drive-or-walk-to-a-certain-coordinate/5332866/2 . `TaskVehicleDriveToCoord` has a different signature (extra straight-line distance, vehicle model hash, and a final bool) — it is a useful A/B test for nearby destinations, not a drop-in replacement.
- **What the working player autopilots actually do (no per-frame re-issue, no cruise/max setters on start):**
  - **Bucko_autopilot** **[verified live]** — https://forum.cfx.re/t/autopilot-standalone-free-release/5330653 : one call, `30.0, 786603, stopRange 10.0`, destination = waypoint blip coords, then a `DriveToWaypoint(...)` helper (arrival monitoring; its body is in the zip, not in the thread text — could not verify). Stop = `ClearPedTasks` + handbrake off + `SetDriveTaskCruiseSpeed(ped, 0.0)`.
  - **Tesla-features autopilot** **[index]** — https://forum.cfx.re/t/tesla-vehicle-features-v1-2/1242199 : one call, `TaskVehicleDriveToCoordLongrange(PlayerPedId(), veh, x, y, z, 20.0, 262579, 1.0)` (262579 = 262144 UseShortCutLinks + 256 + 128 + 32 + 16 + 2 + 1). Speed changes from W/S **re-issue the whole task** with the new speed rather than calling cruise natives. It also notes autopilot "can be stopped by accelerating, braking or steering" — i.e. for a player ped, real driver input is expected to fight/end the task, which is why resources that inject control inputs (§3) matter.
  - Vespura's canonical player example **[verified live]** — https://www.vespura.com/fivem/drivingstyle/ : `SetDriverAbility(ped, 1.0)`, `SetDriverAggressiveness(ped, 0.0)`, then the task — exactly the setup in the mission, confirming ability/aggressiveness are not the differentiator.
- **Per-frame re-issue is NOT the working pattern** and can itself cause crawling: re-issuing a goto task every frame perpetually restarts route calculation / initial acceleration. If the custom resource (or a helper loop) re-issues on a tick, throttle it to "only on destination/speed/style change" — the Tesla resource re-issues only on a key-press speed change **[index, same Tesla source]**.

### 5. Quirks: off-road destination, spawned/teleported vehicle, wrong-way joining

- **Destination off the road network:** "the AI drivers may not know how to get to their destination and will just sit there doing nothing **even on the original map especially if the destination is not on a road/path**… Placement of the waypoints may be critical" **[index]** — https://forum.cfx.re/t/racing-scripts-for-racing-fans/2722830?page=13 . A waypoint blip can sit inside a building/parking structure/field. **Fix/test:** snap the destination to the road first (`GetClosestVehicleNodeWithHeading` / `GetNthClosestVehicleNode` / road-side point) and test with a destination mid-lane on a straight road; if that works, the unsnapped destination (or its final approach over slow flag-10 nodes — parking/driveway nodes, §1) is the crawl at the *end* of routes. Note this explains end-of-route creep better than start-of-route creep.
- **Just spawned / teleported vehicle:** vehicles can be left in a bad physics/streaming state on spawn — a Cfx thread reports spawned vehicles "stuck in place, engine running, wheels can turn, won't move," with `SetVehicleOnGroundProperly` among the attempted fixes and resource-conflict bisection as the diagnostic **[index]** — https://forum.cfx.re/t/issue-with-vehicles-freezing-on-spawn-and-getting-stuck-on-server/5279379 . For the drive task specifically, issuing the task in the same frame as a teleport — before the local node graph around the new position has streamed — risks a failed/stale route. **Fix/test:** engage autopilot only after driving manually for a few seconds at the location; add a short delay + `SetVehicleOnGroundProperly` after any teleport and re-issue the task once.
- **Joining against road direction:** covered in §1 — no AllowGoingWrongWay (512) in any tried style, and ForceJoinInRoadDirection forces a legal-direction join. **Fix/test:** start the test already rolling in the correct lane/direction with a destination straight ahead on the same road. If it then drives at full speed, the bug is route-joining, and the production fix is to add `512` (786603+512 = 787115) and/or drop ForceJoinInRoadDirection, accepting wrong-way lane use when blocked.
- **Switched-off nodes / custom maps:** if the server streams a custom MLO/map or a resource disables roads in an area, longrange routing through that area can stall or detour at crawl speed; UseSwitchedOffNodes changes which of those nodes are routable (§1). **Fix/test:** repeat the test on a vanilla, high-node-density road (e.g. a city arterial and then a freeway — freeway nodes are the fast class, §1) far from any custom map.

## Ranked causes for THIS symptom pattern (fast start → ~1 m/s crawl → stop; reverse fine; off-road fast / on-road slow; manual fine)

| # | Cause | Why it fits | Confirming test / fix |
|---|---|---|---|
| 1 | **Another resource (or a stale/stop path of an autopilot/cruise/limiter resource) re-asserts drive-task speed: `SetDriveTaskCruiseSpeed` / `SetDriveTaskMaxCruiseSpeed` ≈ 0–1, or re-sets driving style** | Task starts at its own 25–50 m/s, cap lands a tick later → crawl at exactly ~1 m/s → stop if 0. Task-only, so manual & reverse unaffected. Bucko proves cruise=0.0 is a common stop-path call on this exact ped. | `grep -r` all resources for those natives + `SetDriveTaskDrivingStyle` + `ClearPedTasks`; stop hits and re-test; bisect by halves on a test server. | 2 | **Leftover/active `AddRoadNodeSpeedZone` with a very low speed (traffic-light sync, props/construction, police traffic control), or the route runs over intrinsically slow nodes** | AI-only, road-only: off-road fast, manual ignores zones/node speeds, initial off-zone segment fast. Speed-0 zones are a documented way to hold AI cars stopped indefinitely. | Test on a remote freeway/arterial far from any placed props/zones; stop traffic/prop/police resources; if crawl follows a *place* not a *vehicle*, it's a zone/node. |
| 3 | **Per-frame brake/throttle injection `SetControlNormal(0, 72/71, …)` from a cruise-control/limiter resource with stuck state** | Player-ped-only (NPC immune); brake control brakes forward drive but *accelerates* in reverse — the only mechanism that cleanly gives "reverse full speed." | Grep for `SetControlNormal`; stop cruise/limiter resources; spawn an NPC driver with the identical task — NPC fast + player slow confirms a player-control-stream cause (this or #1). |
| 4 | **Route joining against node direction: no AllowGoingWrongWay (512) in any tried style; ForceJoinInRoadDirection variant makes it worse; possibly switched-off nodes in the area** | On-road only; car creeps trying to regain the correct lane / reach a legal join, then gives up and stops. Off-road has no lane direction. | Start aligned with traffic, destination straight ahead same road → should be fast. | 5 | **786603's stop bits (StopForVehicles 1 + StopForPeds 2 + StopAtTrafficLights 128) braking for a perceived obstacle/light the tester doesn't count as one** | Produces genuine brake-to-stop on-road; a stopped/parked vehicle it won't steer around can hold it indefinitely. | A/B with style `786468` (reckless avoid, no ped/light stops) and with `0` on an empty straight road. | 6 | **The resource's own post-task calls with a wrong value or wrong native name** (`SetDriveTaskMaxSpeed` is not the documented name — it's `SetDriveTaskMaxCruiseSpeed`; a JS integer instead of a float, or a twice-converted speed, would also cap it) | Cruise *replaces* task speed, so a bad value here silently wins over the correct task argument. | Check F8 for nil-native errors at task start; log the exact arguments; A/B with both calls removed (see #1). |
| 7 | **Destination unsnapped / off-network, or final approach over slow (flag-10) nodes; task issued same-frame as spawn/teleport before nodes stream** | Explains end-of-route creep, "sometimes never moves," and spawn-linked failures; does not explain mid-route crawl on a main road. | Snap destination to closest vehicle node; engage after a few seconds of manual driving at the spot; test a mid-lane destination on a straight road. |
| 8 | **Vehicle-global caps: `SetEntityMaxSpeed`, engine power/torque multipliers, low fuel / `SetVehicleUndriveable`** | Real interference channels (per-frame torque override is documented), **but contradicted** by manual-full-speed and reverse-full-speed in the same vehicle. | Only if the manual/reverse tests were in a different vehicle/state: log fuel + check fresh-spawn vehicle with all vehicle-system resources stopped. Lowest priority. |

**One discriminating experiment that splits the table:** same code, same car, same route, three drivers — (a) player ped as-is, (b) player ped with all non-essential resources stopped, (c) an NPC ped created in the driver's seat. (b) fixes it → cross-resource (#1/#3/#8, grep decides which). (c) fast but (a)/(b) slow → player-specific task/control state (#1/#3). (c) also crawls on-road → road layer (#2/#4/#5/#7), and style `0` + a snapped on-road destination then isolates it further.
